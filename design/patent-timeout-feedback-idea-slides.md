# 一种基于限时执行部分反馈的查询执行计划迭代优化方法：PPT 文稿

依据：[专利交底书底稿](patent-timeout-feedback-disclosure-draft.md)。共 7 页：1 页背景、4 页方案、1 页拟保护点、1 页效果。每页包含可用于汇报的正文和配图建议；[完整英文对照](patent-timeout-feedback-idea-slides-en.md)单独保存。

## 第 1 页｜业务背景：慢候选拖延自动 SQL 调优

**业务场景：** 数据库运维或自动调优平台需要在有限时间窗口内，为一批慢 SQL 寻找更快的执行计划。

**调优方式：** 每轮执行一个候选，通过节点实际行数修正基数输入，再生成下一轮候选；完整运行时间用于比较候选性能。

**慢候选带来的两难：** 一直等待会占用后续迭代的时间，可能在全局预算结束前来不及继续优化；直接取消会中断 `EXPLAIN ANALYZE` 的正常结果路径，若不保存统计，本轮已产生的行数信息就难以继续用于调优。

**超时前已有可用信息：** 有的节点已返回全部相关行数，有的尚未结束但已输出远超估算的行数。这些统计需要按执行状态和计数范围判断，才能作为下一轮输入。

**Idea：** 为每轮候选设置执行期限，超时清理前保留节点统计，经行数判定和合并后用于同一 SQL 的下一轮候选。

**部分反馈：** 整轮候选尚未执行完成时取得的可用节点统计，既包括满足条件的精确行数，也包括行数下界。

**业务目标：控制慢候选的单轮试运行时间，保留并利用已产生的有效节点统计，以降低整体调优耗时，为全局调优预算内的后续有效迭代争取时间，增加发现更优执行计划的机会。**

## 第 2 页｜技术方案一：同一 SQL 的单轮限时迭代

**处理对象：同一 SQL 的多轮候选计划。** Rows Hint 等输入改变规划估算，使优化器产生新的候选；各轮拥有独立的执行上下文。

1. **生成候选：** 原始 SQL 和当前基数反馈共同进入优化器，得到本轮候选计划。
2. **限时试运行：** 使用 `EXPLAIN ANALYZE` 执行候选，初始单轮超时上限 `T₀` 设为 10 秒（当前实验配置，可调整）。
3. **正常完成：** 收集节点统计并更新行数反馈；比较完整运行时间，保留最佳候选。
4. **超时取消：** 在执行器清理前保留原计划及节点观测，判断哪些行数可用；取消结束后，将合格反馈交给同一 SQL 的下一轮候选。

**期限更新：** 未取得完整运行时间时使用 `T₀`；得到同一 SQL 的最佳完整运行时间 `t_best` 后，后续上限取 **`min(T₀, 1.25 × t_best)`**。例如，最佳时间为 4 秒时，上限缩短为 5 秒。

**正常完成和超时取消都可提供行数反馈；仅完整运行时间用于更新最佳候选和超时上限。实际期限还受剩余全局调优预算约束。**

**建议配图：** 使用[图2：系统与反馈位置](patent-timeout-feedback-figures/png/fig2-system.png)。展示第 i 轮候选的两类结果：正常完成与超时取消均进入行数反馈，用于生成第 i+1 轮候选；正常完成的运行时间同时用于比较最佳候选。

## 第 3 页｜技术方案二：超时返回节点行数与执行状态

**核心处理：超时取消时，在执行器清理前读取并返回节点行数和执行状态，供后续行数反馈判定。**

1. **保存节点对象：** 从 `QueryDesc.planstate` 取得顶层算子的 `PlanState`，遍历执行计划状态树并保存节点指针。
2. **读取行数：** 通过 `PlanState.plan` 读取 `Plan.plan_node_id` 和 `Plan.plan_rows`，得到节点 ID 和估算 E；通过 `PlanState.instrument` 读取 `Instrumentation.ntuples` 和 `nloops`，得到累计返回行数 A 和 Loops。
3. **读取执行状态：** 根据 `Instrumentation` 的调用起始时间判断 `active`。`active=false` 表示没有正在进行的 `get_next` 调用；此时若 `Instrumentation.status != 0`，则记为 `terminal=true`，表示本地已读到 EOF。
4. **返回本轮统计：** 返回实际执行计划文本、节点行数及执行状态，供客户端进行行数判定并更新后续基数反馈。

**本地 EOF 不直接等于精确行数，还需检查节点是否会再次执行，以及实际与估算行数能否直接比较。**

**配图：** [图3：读取 GaussDB 算子执行统计](patent-timeout-feedback-figures/png/fig3-executor-observation-flow.png)。结构体字段来源和状态计算公式见图中说明。[可编辑 PPT](patent-timeout-feedback-figures/pptx/fig3-executor-observation-flow.pptx)。

## 第 4 页｜技术方案三：检查算子是否还会再次执行，以及行数能否直接比较

**检查行数来自哪个扫描或连接。** 查询块、SQL 谓词、连接类型和运行参数应保持一致，才能更新该扫描或连接的 Rows Hint。

**区分单次返回行数与累计返回行数。** 只有实际行数与估算覆盖相同执行次数时才能比较。若使用多次执行累计的 A，估算 E 也必须按相同执行次数换算。

**检查父算子是否还会再次执行子算子。** 当前调用返回 EOF，只能说明这一次执行已结束。还需检查候选若继续执行，父算子是否仍会请求后续输出，确认该扫描或连接已返回全部相关行数。

**两个典型例子：**

- Nested Loop 内侧连接第一次返回 EOF 后，下一条外侧行仍可能使内侧连接重新执行。
- 内侧算子执行 20 次，每次估算 10 行、实际返回 5 行。累计返回 100 行不能与单次估算 10 行直接比较；应比较单次实际 5 行与估算 10 行，或把估算换算为 20 次执行的总行数。

**配图：** [图7：再次扫描与累计行数的比较](patent-timeout-feedback-figures/png/fig7-reentry-scope.png)。[可编辑 PPT](patent-timeout-feedback-figures/pptx/fig7-reentry-scope.pptx)。

## 第 5 页｜技术方案四：节点行数反馈的判定与合并

**更新原则：精确行数覆盖，行数下界只抬高，没有可用行数时保持原值。** A 为截至统计采集时已返回的行数，E 为按相同执行次数计算的估算行数。正常完成与超时取消均按以下条件判定。

| 检查结果 | 反馈类型 | 下一轮 Rows Hint 更新 |
| --- | --- | --- |
| 该扫描或连接已返回全部结果，父算子不会再次执行它 | **精确行数 `EXACT`** | 用 A 更新，可上调或下调，并清除旧下界 |
| 尚不能确认已返回全部结果，已返回行数只增不减，且 A > E | **行数下界 `LOWER_BOUND`** | 尚无精确值时保留已有 Hint 与 A 中较大的值；已有精确值时保留精确值 |
| 未执行、无法按相同执行次数比较，或尚未返回全部结果且 A ≤ E | **不更新 `NONE`** | 保持已有 Rows Hint |

**合并规则：** 多个下界取最大值；采样值不覆盖已采用的精确行数或下界；同一轮、同一扫描或连接的精确值按计划树遍历顺序首个生效。

**更新示例：** 初始采样为 5,000；取得可用于反馈的下界 2,400，Hint 仍为 5,000，同时保存下界；随后下界达到 6,400，Hint 提高到 6,400；取得精确行数 7,200 后，更新为 7,200 并清除旧下界。

**算子尚未返回全部结果且 A ≤ E，不能据此确认估算过高。** 未执行的算子没有 A-rows；已执行但返回零行的算子，A-rows=0。

**配图：** [图5：行数分类与 Rows Hint 更新](patent-timeout-feedback-figures/png/fig5-evidence.png)。[可编辑 PPT](patent-timeout-feedback-figures/pptx/fig5-evidence.pptx)。

## 第 6 页｜拟保护点：限时执行中的节点行数判定与跨轮反馈

**拟保护的核心链条：**

**同一 SQL 候选限时执行 → 取消清理前取得节点统计 → 判定精确值、可用下界或无反馈 → 分级合并 → 修正下一轮基数。**

1. **限时取消时保留统计：** 候选达到单轮期限被取消时，在执行器清理前取得节点估算行数、已返回行数及执行状态。
2. **判定可反馈的行数：** 根据执行状态、是否还需再次调用，以及实际与估算的计数范围，区分精确行数、可用下界和无反馈。
3. **按反馈类型跨轮合并：** 精确行数可上调或下调；合格下界只抬高；无合格统计保持原值。精确值优先于下界，多个下界取最大值。
4. **修正下一轮候选：** 将合并结果用于同一 SQL 的下一轮独立规划。正常完成也可提供行数反馈；完整运行时间用于比较最佳候选和调整后续期限。

**可进一步限定：** 尚未返回全部结果的节点，只有实际行数和估算可直接比较且 A > E 时才以合格下界抬高基数；单轮期限同时受配置上限、最佳完整时间和剩余调优预算约束。

**技术重点：** 期限取消、清理前读取、行数适用判定和跨轮合并构成连续处理流程，兼顾有效反馈保留与候选性能评价。

## 第 7 页｜业务价值与验证：减少等待，为有效迭代争取时间

**价值一：控制单轮试运行时间，保留有效反馈，降低整体调优耗时。** 限制慢候选的试运行时间，并将超时前取得的合格节点统计继续用于下一轮基数修正。在现有工作负载对照中，相较于无单轮超时组，JOB 的整体调优耗时下降约 32%，JOB-complex 下降约 42%。

**价值二：为全局预算内的后续有效迭代争取时间，增加发现更优执行计划的机会。** 当反馈能够改变基数输入时，节省的等待时间可用于后续候选试运行。以 JOB `16b` 为例，无单轮超时组完成 4 轮后因全局预算条件结束调优，交付候选的完整执行时间约为 36 秒；10 秒组进行了 11 轮部分反馈迭代，形成更快的恢复候选，独立测量的完整执行时间约为 11 秒。该恢复候选当时未正式交付。

**实验设置：** JOB 113 条、JOB-complex 30 条 SQL；比较无单轮超时组与 10 秒部分反馈组；两组全局调优搜索预算均为 300 秒、`patience-iters=5`。10 秒指初始单轮上限，后续按最佳完整运行时间动态缩短。

**调优总时长：**

| 数据集 | 无单轮超时组 | 10 秒部分反馈组 | 降幅 |
| --- | ---: | ---: | ---: |
| JOB | 2,348 秒 | 1,599 秒 | 31.89% |
| JOB-complex | 1,002 秒 | 583 秒 | 41.84% |

**完整执行时间总和（扩展评估）：**

| 数据集 | 原始 SQL | 无单轮超时组 | 10 秒部分反馈组 |
| --- | ---: | ---: | ---: |
| JOB | 456 秒 | 190 秒 | 168 秒 |
| JOB-complex | 332 秒 | 48 秒 | 47 秒 |

**评估方法：** 秒数取整，比例按未舍入数据计算。JOB 扩展评估包含 `16b`、`18c` 两条未正式交付的恢复候选；若只采用正式交付并回填原 SQL，10 秒组总执行时间约为 205 秒。因此，实验支持工作负载级调优时长下降，执行效果结论取决于采用哪些候选，不代表每条查询都改善。两组使用不同代码版本。

## 汇报依据与讲解边界

- 专利名称统一为“一种基于限时执行部分反馈的查询执行计划迭代优化方法”。“部分”指整轮候选尚未执行完成，已完成节点仍可提供合格精确行数。交底书正文保留技术事实、实施条件和实验结果，文献评价与实现差距见[独立核对记录](patent-timeout-feedback-manuscript-audit.md)。重新规划和原计划匹配属于实施防护，不列入第 6 页拟保护点。
- 第 2 页的期限更新规则已核对 [`feedback_effective_timeout`](../contrib/hint_adviser/hint_adviser_feedback_round.c) 和[需求串讲第 3.1 节](超时EXPLAIN_ANALYZE部分反馈需求串讲.md)。10 秒来自[当前实验配置](../data/patience5-ab-20260928/run-manifest.txt)，是可配置的初始单轮上限。全局预算还需为取消、取证及重新规划保留 8 秒。
- 第 3 页已核对服务端[`start_completion_capture`、`collect_execution_evidence`、`emit_partial_snapshot`](../contrib/extopt-gaussdb/extopt_partial_capture.cpp)、[`partial_gaussdb_execution_capture_evidence`](../contrib/extopt-gaussdb/extopt_partial_gaussdb.cpp)及[需求串讲第 4.4–4.5 节](<../sources/requirements/超时EXPLAIN_ANALYZE需求串讲.md>)。服务端快照包含实际执行计划的文本和已取得的算子统计，完整 JSON 计划树由客户端对相同候选重新规划取得。未执行节点不写成零行统计。
- 第 4–5 页描述交底书拟议的行数检查与更新条件。当前原型已有超时统计捕获、分类和合并。仍需补齐对所有算子的再次执行检查、单次与累计行数换算，以及不同轮次 SQL 谓词、参数和数据的检查，不能根据性能对照宣称这些条件已全部验证。
- 第 5 页的更新规则已核对[需求串讲第 4.8 节](<../sources/requirements/超时EXPLAIN_ANALYZE需求串讲.md>)及[`rows_hint_merge` 实现](../contrib/hint_adviser/hint_adviser_rows_state.c)。同轮精确值首个生效，后续轮的精确值可以更新旧精确值；多个可信下界取最大值；新下界超过已有精确值时只记录矛盾诊断，仍保留精确值。仅内部下界增强而 Hint 输出不变时，不算 Rows 输出发生变化。示例说明的是合格证据的合并，不假定本轮计划估算始终等于历史 Hint 值。
- 业务价值分为减少单个候选等待与争取后续有效迭代机会。总轮次不保证增加：JOB 为 569 → 528，JOB-complex 为 166 → 182；资源占用改善尚未独立测量。`16b` 的恢复候选与正式交付的区别见[逐 SQL 分析](patent-timeout-feedback-job-execution-attribution.md)。
- 实验值已依据[逐查询输入记录](../data/patience5-ab-20260928/results/workbook-input.tsv)重新计算。完整候选执行时间采用交底书预先指定的第 3 次独立运行结果。
