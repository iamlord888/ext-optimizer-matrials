# 五件数据库专利的方法流程逐步解析

本文根据五件英文授权专利的原始 PDF、说明书和权利要求，逐步还原每件专利实际描述的方法流程。原始文件见[专利原件索引](patent-originals/MANIFEST.md)，逐条引文核对见[引证核对笔记](../sources/patents/quote-audit.md)。本文重点回答四个问题：

1. 查询或候选计划在什么时点被停止；
2. 专利取得的“实际信息”来自什么对象、覆盖什么范围；
3. 专利如何判断这些信息足以触发下一步动作；
4. 下一步动作是当前查询重优化、未来查询反馈、进度显示，还是计划级性能淘汰。

本案拟描述的流程是：对外部调优器生成的真实候选设置单轮期限；期限到达后取消候选；在执行器清理前读取原计划和节点运行事实；将每个节点事实绑定到具体基数目标和调用范围；按目标级完成性输出 `EXACT`、`LOWER_BOUND` 或 `NONE`；把合格证据送入下一轮独立候选。下面的五件专利分别覆盖其中若干构件，但消费对象和判断顺序不同。

## 一、IBM `US7716215B2`：Progressive Query Processing

原件：[US7716215B2.pdf](patent-originals/US7716215B2.pdf)；[英文公开文本](https://patents.google.com/patent/US7716215B2/en)。

### 1. 解决的问题

IBM 认为，传统流程在编译期依据静态统计生成 QEP，之后直接执行；如果基数估算错误，连接方法和连接顺序可能严重不合适。该专利的目标是让**当前正在执行的查询**在运行中发现误估后暂停，并依据已经得到的实际信息重新规划。

说明书 `p-0040` 将核心概括为在 QEP 中加入检查点，比较 “the optimizer's cardinality estimates with the actual number of rows processed thus far”；说明书 `p-0044` 进一步定义，`CHECK` 没有关系代数语义，而是一个用于验证估算的断言算子。

### 2. 总体流程

#### 步骤 1：编译 SQL，生成初始 QEP

1. SQL 编译器解析、改写并优化查询。
2. 优化器根据统计信息生成初始 QEP，并为节点估算基数、代价和剩余执行工作量。
3. 优化器在选出物理计划后进行 post-pass，根据估算可靠性、误估可能造成的损害以及计划上方是否存在依赖该基数的连接，选择是否插入检查点。[p-0076][p-0078][p-0079]

#### 步骤 2：为检查点确定可接受的基数区间

1. 每个 `CHECK` 具有一个基数区间 `[l,u]`。
2. 区间不是简单固定常数，而是由检查点下方节点的估算基数以及检查点上方剩余 QEP 的敏感性得到。
3. 例如，Nested Loop Join 的外侧行数如果超过某个交叉阈值，Hash Join 或 Merge Join 可能比 Nested Loop 更合适；该交叉范围可以用来设置检查条件。[p-0044][p-0112][p-0113]

#### 步骤 3：选择检查点实现形式

专利描述了五类实现。它们的共同点是检查“运行时实际输出是否仍处于计划可接受范围”，但触发时机和已经输出的结果处理方式不同。

1. **Lazy Checking（LC）**：把 `CHECK` 放在已有物化点之后。子计划先完整物化，物化结束后一次性检查其精确基数。由于此时没有结果流出，重优化时可以直接复用物化结果。[p-0052][p-0056]
2. **Lazy Checking with Eager Materialization（LCEM）**：计划中没有物化点时，显式插入 `CHECK-MATERIALIZATION` 对，使中间结果先完整物化，再检查。专利建议主要放在 Nested Loop 外侧，因为原优化器已经估计其外侧较小。[p-0058][p-0059]
3. **Eager Checking without Compensation（ECWC）**：把检查点放在某个物化点下方，允许在整个中间结果物化之前发现误估；因为检查点上方仍有物化边界，之前没有向用户输出的流水结果，所以不需要去重补偿。[p-0062][p-0063]
4. **Eager Checking with Buffering（ECB）**：在检查点设置缓冲区，先缓存经过的行，直到可以确定检查成功或失败。对于区间 `[0,b)`，若第 `b` 行进入缓冲区则失败；若子节点返回 `EOF` 且缓冲区少于 `b` 行则成功。检查失败时触发重优化，检查成功时继续流水线。[p-0065][p-0066]
5. **Eager Checking with Deferred Compensation（ECDC）**：不阻塞流水线，行仍然继续传给父算子和用户；同时通过 `INSERT` 把已经返回行的唯一标识写入临时 side table。若之后重优化，新的结果流在顶层增加 anti-join，排除已经返回的行，避免重复输出。[p-0068][p-0069]

#### 步骤 4：执行 QEP，检查实际输出

1. 执行器运行初始 QEP。
2. `CHECK` 读取其下方节点的计数器或物化结果计数。专利 `p-0070` 说明，如果数据库已经为每个算子维护计数器，`CHECK` 可以直接读取下方算子的计数。
3. 检查当前实际基数 `a` 是否处于 `[l,u]`。
4. 如果 `a` 在区间内，检查成功，查询继续执行。
5. 如果 `a` 超出区间，检查失败，当前查询执行被终止，进入重优化。

这里存在一个很重要的方向差异：如果实际输出已经超过上界，通常可以立即判断失败；如果实际输出一直低于下界，必须等子流返回 `EOF` 才能确认最终输出确实低于下界。`p-0065` 对此有明确描述。

#### 步骤 5：在失败现场保留中间结果和运行统计

1. 检查失败后，运行时保留已经计算的中间结果，并将其提升为临时物化视图。
2. 临时视图的目录统计记录实际基数；专利还允许记录更详细的统计，如列的最小值和最大值。
3. `p-0088` 明确说，统计可以针对 QEP 的所有节点，而不只是物化点。
4. 这些事实被提供给递归调用的 SQL 编译器和优化器。

#### 步骤 6：重新优化当前查询

1. 递归调用 SQL 编译器或直接调用查询优化器。
2. 优化器同时考虑两类候选：
   - 复用已有临时物化结果的候选计划；
   - 丢弃部分已完成工作、重新计算中间结果的候选计划。
3. 优化器使用更新后的基数和其它实际统计给候选计划估价。
4. 选出代价最优的重优化计划。专利 `p-0086` 明确说明，已经计算的中间结果并不总是应该复用，因为错误的初始连接顺序可能已经产生了过大的中间结果。

#### 步骤 7：从新计划继续执行并处理重复结果

1. 若采用 LC、LCEM 或 ECWC，通常从物化边界继续执行，复用或重新计算中间结果。
2. 若采用 ECB，先处理缓冲区中的行，再从下方算子继续请求行。
3. 若采用 ECDC，重新执行计划并通过 side table 的 anti-join 排除已经返回的行。
4. 新计划还可以再次加入检查点，形成连续的 progressive re-optimization。

### 3. 这件专利与本案的关系

IBM 最接近本案的部分是：运行中比较估算和实际、使用 `EOF` 判断低输出、用超过阈值的前缀输出发现低估、以及把节点统计用于后续重优化。

但 IBM 的主流程是**当前查询内部预置检查点触发的重优化**。它并没有明确描述：外部调优器在任意节点取消候选后，遍历原计划所有节点，并按未来重入、调用范围和累计/单次计数口径，把节点事实统一分成 `EXACT`、`LOWER_BOUND`、`NONE`。IBM 的检查点本身已经把可接受区间和检查语义预先嵌入计划；本案拟处理的是取消现场的事后证据判定。

## 二、Oracle `US11321317B2`：自适应计划、自动重新优化和提前终止

原件：[US11321317B2.pdf](patent-originals/US11321317B2.pdf)；[英文公开文本](https://patents.google.com/patent/US11321317B2/en)。

这件专利包含两条容易混淆的流程：**adaptive plan execution** 服务当前查询；**automatic reoptimization** 服务同一或相似查询的后续执行。专利 `[0083]` 明确区分了二者。

还要补充一层背景：说明书 `[0009]` 明确讨论了“catastrophic plan”。如果计划运行时间过长，用户或 DBA 可以终止（kill）该计划；在传统做法中，终止后还需要用户手工修改计划，避免同一计划再次被选中。这个背景说明 Oracle 专利确实考虑了“长时间运行计划被人为终止”的问题，但 `[0009]` 本身没有规定终止后自动读取每个执行器节点并进行证据分级。

### 1. 自适应计划执行：当前查询内部切换子计划

#### 步骤 1：编译包含多个子计划的 adaptive plan

1. 优化器为一个查询生成一个包含多个候选子计划的 adaptive plan。
2. 例如，一个决策点前后同时准备：
   - Index Range Scan + Nested Loop Join；
   - Table Scan + Hash Join。
3. 计划中插入 statistic collector。collector 可以是 rowsource，也可以内置在现有 rowsource 中。[0037][0039]

#### 步骤 2：执行到统计收集点

1. 查询开始按 adaptive plan 执行。
2. collector 已经作为执行计划中的 rowsource 或现有 rowsource 的一部分被编译进去，因此它是在**查询执行过程中**随算子读取、产生行，而不是查询开始前单独执行一条简单统计查询。
3. collector 读取表扫描、过滤或 Hash Join 产生的行。
4. collector 可以只根据已读取表的一个严格子集生成统计；例如统计满足谓词的行数、不同值数量、最大值和最小值。
5. collector 旁边可以有 buffer，暂存已经读取的行，避免在尚未确定使用哪个子计划前就建立 Hash Table 或启动 Nested Loop。[0041][0042]

#### 步骤 3：达到收集阈值并评价子计划条件

1. 当 collector 读取的行数达到 buffer 或统计阈值时，触发决策点。
2. 将运行时行数、选择率或其它特征与编译期条件比较。
3. 根据条件选择一个子计划。例如，实际选择率低于阈值时选择 Index + NLJ，高于阈值时选择 Table Scan + Hash Join。
4. 决策点之前已经执行的部分通常是多个子计划共用的前缀；决策完成后，缓冲行交给被选中的子计划，未选中的子计划在本次执行中不再运行。

#### 步骤 4：为后续执行记录选择结果

1. 将本次选择的子计划写入 cursor 的 sub-plan indication data。
2. 后续相同或语义等价查询可以直接复用这次选择，跳过部分统计收集和决策过程。[0045]

这条流程是当前查询内部的自适应分支选择，不等于“取消查询后保存节点证据”。

### 2. Automatic Reoptimization：部分执行统计用于未来查询

这里的“部分执行”首先指**第一条查询的执行计划只运行了全部计划的一部分**：例如只执行了第一计划或其中一段，随后因为运行中切换、提前终止或其它执行结束原因停止。`[0088]` 的表述也是“the first execution plan (or a portion thereof) is executed”，统计收集器从该计划已经执行的操作中取得行数和其它统计。它不是把原始 SQL 拆成若干个简单 SQL 再分别获取结果。专利中另有 dynamic sampling 等编译期统计查询，那是独立的数据来源和执行阶段，不能与 `[0083]` 的运行期部分执行混为一谈。

#### 步骤 1：生成第一执行计划并保存估算

1. 对第一条查询生成第一执行计划。
2. 计算第一计划或其子部分的估算成本。成本可以包含处理行数、磁盘访问、比较次数、机器周期或时间。[0086]
3. 该估算可以针对整个计划，也可以针对单个操作或子计划。

#### 步骤 2：执行第一计划并收集操作统计

1. 执行第一计划或其一部分。[0088]
2. 一个或多个 statistic collector 在运行中统计操作产生的行数。
3. 统计可以在多个层级取得：总计划、某个子计划、某个表扫描、某个连接或其它操作。[0089]
4. 并行执行时，先汇总多个 worker 的实际工作量，再得到操作级实际成本。[0090]

#### 步骤 3：比较估算与实际

1. 在 `[0091]` 的流程中，将实际成本与相应估算成本比较。
2. 比较可以针对整个第一计划，也可以针对一个或多个子部分。
3. 用阈值或其它 heuristic 判断差异是否显著；例如实际成本超过估算两倍时触发保存或重新优化。[0092]

这里的“可用”不是“已经证明是最终完整基数”的意思。Oracle 至少有三种使用方式：

- **用于 adaptive plan 决策：** 只要已读取的行数、选择率或不同值数量足以区分子计划条件，就可以选择某个子计划；统计可以只来自已读取表的严格子集。[0037][0042]
- **用于 in-flight reoptimization：** 只要运行统计足以证明当前计划的估算明显失真，且结合剩余操作成本可以证明替代计划更有利，就可以终止当前计划并换计划；不需要先知道最终完整行数。[0105]-[0107]
- **用于后续查询反馈：** 统计差异达到保存阈值时，按数据库对象和操作建立统计或 plan directive；后续查询还要检查对象、操作、谓词结构或 bind value 是否相关，差异过大时不复用旧统计。[0098][0114]-[0117]

所核文本没有给出本案意义上的 `EXACT`、`LOWER_BOUND`、`NONE` 判定。它没有明确要求沿父链排除未来重入，也没有规定累计 `OUTPUT_ROWS` 与单次调用估算不一致时必须拒绝反馈。换言之，Oracle 的可用性判断是“是否足以支持当前决策或后续匹配”，本案拟解决的是“是否具有可证明的目标级行数语义”。

#### 步骤 4：保存可复用的统计或 plan directive

1. 如果差异足够大，保存与某个数据库对象和操作关联的统计。
2. 说明书 `[0083]`、`[0084]` 明确允许首次执行是完整执行，也可以是部分执行；可保存表、连接、分组、索引的基数等运行信息。
3. `[0087]` 允许在多个操作之后设置收集器，并把至少部分信息反馈给下一次相似查询的优化器。
4. 另一种实现保存 plan directive。plan directive 可以指出发生误估的表、列或连接类型，但可以不保存原查询的具体谓词和 bind value，以便跨多个相似查询使用。[0114][0115]

#### 步骤 5：收到后续查询并判断统计是否适用

1. 后续查询到达时，查询优化器检查 cursor 或 plan directive 存储区。
2. 如果是相同或语义等价查询，直接判断已有统计是否可用。
3. 如果 bind value 不同，判断两个 bind value 的选择率是否“相似 enough”。
4. 如果差异过大，则不使用涉及该 bind value 的旧统计。[0098]
5. 如果统计与后续查询相关，生成第二执行计划并执行。[0093][0094]

授权权利要求 1 还给出了更窄的实施方式：针对第一执行计划中的一个操作，比较估算性能和实际性能；差异达到条件后仅保存该操作的统计；收到不等价的第二查询时，按数据库对象和操作识别统计，再生成第二计划。

### 3. In-flight Reoptimization：当前查询提前终止并换计划

Oracle `[0105]`–`[0107]` 的上下文比单纯的“运行中发现误估后换计划”更具体：系统会同时考虑误估程度、剩余操作数量和剩余操作的估计成本。

1. **开始执行第一计划。** 当前查询按照编译期选定的执行计划运行，统计收集器在早期操作中记录行数、成本或其它运行信息。
2. **比较运行事实和编译估算。** 例如，表扫描上的谓词实际产生 10,000 行，而编译期估算只有 100 行；也可以比较某一早期子计划的实际成本与原估算成本。
3. **判断是否值得切换。** 终止条件不只取决于误差倍数，还可以考虑计划中剩余多少操作、剩余操作的估计成本，以及重新生成计划的收益。[0106]
4. **重新计算候选计划成本。** 使用已经收集的运行统计，重新计算当前计划剩余部分的总成本，并估计另一个候选计划的总成本。如果替代计划的更新后成本明显更低，则当前计划被判定为不再值得继续执行。[0107]
5. **终止当前计划并启动另一个计划。** 当前执行计划在完整结束前被停止，查询被重新优化或重新编译，随后启动不同的执行计划。[0105]

Oracle 对“已经执行了一部分的结果如何接入新计划”给出了框架层面的两种可能：在 adaptive plan 的一般描述中，替代计划可以使用原计划已经产生的部分结果，也可以从头开始执行；但 `[0105]`–`[0107]` 并没有规定一个类似 IBM 临时物化视图或 ECDC anti-join 的统一结果复用协议。能否复用，要取决于具体 adaptive plan、buffer 和执行器实现。[0026][0054]

### 4. 终止背景、in-flight 重优化与 automatic reoptimization 的关系

这三部分在同一件专利中相关，但消费对象不同：

| 流程 | 触发方式 | 处理对象 | 后续动作 |
| --- | --- | --- | --- |
| Catastrophic plan 背景 | 用户或 DBA 认为计划运行过久而 kill | 一个运行过久的计划 | 背景中要求采取措施避免再次选择，未在 `[0009]` 单独规定节点快照分类 |
| In-flight reoptimization | 运行中实际统计显著偏离估算，且切换具有成本收益 | 当前查询的正在执行计划 | 停止当前计划，重新编译或重新优化，启动其它计划 |
| Automatic reoptimization | 第一执行产生显著误估统计，后续收到相同、等价或相关查询 | 可持久化的操作统计、plan directive 或 cursor 信息 | 后续查询生成新计划 |

因此，Oracle 专利确实同时涉及“用户终止长计划”和“运行中提前终止换计划”，这使它比此前概括的“部分执行统计反馈”更接近本案。仍然没有在所核文本中看到本案的完整顺序：外部固定期限触发取消、执行器清理前保存全树节点事实、按父链未来重入和调用口径判断每个 A-rows 的证据等级，再将合格证据送入下一轮独立候选。Oracle 的强重合点应改写为：**部分执行、用户/系统终止、运行中换计划、操作级统计和后续查询反馈均已公开；本案拟补充的是取消现场的目标级证据证明与分级消费。**

## 三、Microsoft `US11334538B2`：CE Feedback Loop

原件：[US11334538B2.pdf](patent-originals/US11334538B2.pdf)；[英文公开文本](https://patents.google.com/patent/US11334538B2/en)。

这件专利描述的是一个“查询主机 + 外部优化服务”的反馈基础设施。它的主线不是在查询内部切换计划，而是把查询执行期间或结束时产生的事件交给反馈服务，生成后续查询的变更建议。

### 1. 系统组成

1. **Query Host**：执行 SQL、生成计划和基数估算。
2. **Query Processor**：按照计划执行查询。
3. **Monitors / Query Signal Generator**：监控运行时行数、CPU、内存等，生成事件信号。
4. **Optimization Service Host**：可以独立于 Query Host 部署。
5. **Signal Router**：接收事件并路由给合适的分析器。
6. **Query Plan Signal Analyzer**：从事件中分析实际基数、估算基数及相关查询参数。
7. **Feedback Manager**：生成变更建议并返回 Query Host。
8. **Query Store / Data Store**：保存历史查询、计划、实际/估算基数、建议和状态信息。[0024][0026][0043]-[0059]

### 2. Flowchart 300：一次 CE feedback 生成流程

#### 步骤 1：Query Host 执行第一条查询

1. Query Host 为第一条查询生成计划和估算基数。
2. Query Processor 执行查询。
3. Monitor 在执行期间或完成时收集运行时统计。
4. Query Signal Generator 将统计封装为事件信号，例如 XEvent 消息。[0024][0062]

事件可以包含：实际基数、估算基数、计划参数、CPU、内存、连接类型、索引设置、相关性和其它运行信息。`[0026]` 明确 profile data 可以包含计划中**每个节点**的 estimated/actual cardinality。

#### 步骤 2：Signal Router 路由事件

1. 外部优化服务的 Signal Router 接收事件流。
2. 根据事件中的查询、监控器或分析器标识，选出对应的 Query Plan Signal Analyzer。
3. 将事件或事件子集发送给分析器。[0063]

#### 步骤 3：Analyzer 分析实际基数和查询参数

1. Analyzer 从运行时统计中确定被查询数据的实际基数。
2. 找出与估算基数关联的查询模型参数，例如列相关性、内存 grant、连接类型、索引、containment、TVF 交错优化和 table variable 延迟编译。[0064][0074]
3. 对比 estimated cardinality 与 actual cardinality。
4. 还可以分析列相关性以及 CE 估算是否出现振荡。[0072][0073]

#### 步骤 4：Feedback Manager 生成建议

1. Feedback Manager 接收 Analyzer 的分析结果和历史数据。
2. 根据估算与实际基数差异，决定修改哪个查询参数以及修改程度。[0065]
3. 修改形式可以是：额外 query hint、join hint、filtered statistics、更新统计分布、替换 CE model 或其它模型/数据库设置。[0026][0028]
4. 如果检测到估算来回振荡，可以保存“暂时关闭反馈”的状态，防止反馈循环不断反向修正。[0073]

#### 步骤 5：将建议返回并持久化

1. Feedback Manager 经反馈连接（例如 TDS）向 Query Host 发送建议。[0030][0066]
2. Query Host 将建议写入 Query Store 或其它持久化位置。
3. 建议可以自动应用，也可以通过 UI 展示给用户选择；还可以支持回滚。[0031][0053]

### 3. Flowchart 600/700：后续查询消费建议

1. Query Host 后续收到同一查询或相似查询。[0077][0086]
2. Monitor 判断是否与此前查询相同或相似。相似条件可以是相同表、表连接顺序、连接谓词、搜索谓词或部分相同输出。[0087][0089]
3. Query Host 接收已有 change recommendation。[0079]
4. Query Processor 根据建议和新的估算基数生成第二计划。[0080]
5. 执行第二查询，并再次收集运行事件。[0082][0083]
6. 新事件返回外部优化服务，形成下一轮 feedback loop。[0084]

### 4. 与本案的关系

这件专利已经公开“节点级实际/估算基数—后续查询 CE feedback”的完整反馈链，也公开了执行中事件。因此不能把“节点级 A-rows 反馈后续优化”本身作为宽泛发明点。

所核文本没有明确规定：外部单轮期限取消后，必须在执行器清理前读取原计划；必须沿父链判断未来重入；必须区分完整值、下界和无反馈；必须把取消候选的部分时间与完整候选时间分离。本案的区别应集中在这些取消现场的证据语义条件。

## 四、Microsoft `US7493337B2`：Query Progress Estimation

原件：[US7493337B2.pdf](patent-originals/US7493337B2.pdf)；[英文公开文本](https://patents.google.com/patent/US7493337B2/en)。

这件专利的目标是估计并显示当前查询已经完成多少工作。它有节点级上下界和算子规则，但最终输出是进度显示，不是被取消候选的下一轮计划反馈。

### 1. 建立查询工作量模型

1. 接收查询并生成执行计划。
2. 根据查询特征把执行计划分成一个或多个 pipeline。
3. 选择每个 pipeline 的 driver operator。
4. 以 driver 节点的估算基数或工作量估计总工作量。
5. 执行期间估计已经完成的工作量，并计算进度比例。[权利要求 1][p-0031]

专利指出，仅使用“已经输出的根节点行数”不够，因为有的查询很晚才输出行；仅按“已经完成的算子数”也不够，因为单 pipeline 中多个算子可能同时处于活动状态。[p-0004][p-0121]

### 2. 为每个算子维护上下界

#### 步骤 1：初始化叶节点边界

对 Table Scan、Index Scan 等叶节点，通常可以从系统目录得到表或索引的精确行数，因此上下界可以相同。[p-0092]

#### 步骤 2：执行时更新算子输出计数

每个计划节点维护当前已经输出的元组数 `K_i`。随着执行推进，重新计算该节点可以输出的总行数上下界。[p-0091][p-0092]

#### 步骤 3：按物理算子规则传播边界

专利给出了一组示例规则：

- Filter：已输出 `K_i` 作为下界，上界根据前一节点未处理部分加已输出量计算；
- Group By：已观察到的不同值数量 `d` 可以收紧下界；
- Sort：已输出数量可以形成下界，输入上界形成输出上界；
- Nested Loop：根据外侧未处理行数、内侧上界和已经输出数量计算上下界；
- Hash Join：利用最大 build partition 大小 `S` 限制每个 probe 行最多产生的输出；
- Index Seek：已输出数量是下界，基础表大小可以作为上界。[p-0093][p-0094]

#### 步骤 4：判断优化器估算是否位于边界内

1. 将当前优化器估算 `N_i` 与 `[LB_i, UB_i]` 比较。
2. 如果 `N_i` 位于区间内，保留当前估算。
3. 如果 `N_i` 超出区间，将估算修正到违反的边界或区间内的值。[p-0089][p-0091]
4. 某个节点边界变紧后，可以向计划树上方传播，进一步收紧 Group By、Sort 等节点的边界。[p-0090]

#### 步骤 5：计算并显示进度

1. 使用已完成工作量和总工作量估计计算当前进度。
2. 为避免进度条倒退，使用总工作量上界计算一个单调进度值。
3. 可以同时显示更准确但可能非单调的进度，以及基于上界的单调进度。[p-0101][p-0102]

### 3. 中止入口的含义

权利要求 42 的系统包含允许用户开始或 abort 查询的输入设备。该入口服务于“用户看进度后决定继续还是中止”的交互流程。权利要求 27 的“已输出项目数作为下界”属于另一条从属权利要求链，所核文本没有说明用户中止后把该下界写入未来独立候选的 Rows 输入。

### 4. 与本案的关系

该专利最接近本案的部分是：它明确为多个算子维护输出计数、上下界和算子特定的可信边界。它提供了“某个运行中数值何时足以修正估算”的思想。

但其判定对象是**当前查询进度模型**，不是取消后要持久化到下一轮调优的节点证据。它没有将用户 abort 与后续候选计划反馈连在同一流程中，也没有以父链未来重入和累计/单次调用口径作为节点 A-rows 的可信性条件。

## 五、Sybase `US9213740B2`：Automatic Tuning of Database Query Optimizer

原件：[US9213740B2.pdf](patent-originals/US9213740B2.pdf)；[英文公开文本](https://patents.google.com/patent/US9213740B2/en)。

Sybase 的目标是升级数据库软件时避免新优化器产生性能回退。其反馈对象是**候选计划的执行性能**，不是节点基数。

### 1. 建立 baseline best plan

1. 收到一个查询。
2. 使用旧版本优化器生成旧计划，或从已有 Abstract Plan 得到旧计划。
3. 将旧计划作为 baseline best plan。
4. 对查询文本、用户和影响语义的 session setup 建立 learning object，用于关联该查询的 best、bad 和 candidate 计划。[p-0052][p-0053][p-0058][p-0096]

### 2. 新优化器生成候选计划

1. 新版本优化器开始搜索。
2. 如果 learning object 中已有 best AP，用它 priming 搜索空间。
3. 如果生成的计划匹配已知 bad AP，则跳过该计划，直接使用当前 best AP。
4. 如果是此前没有见过的新计划，则将其记录为 candidate AP，准备进入训练阶段。[p-0057][p-0075][p-0190][p-0192][p-0193]

### 3. 多次执行候选并聚合性能

1. candidate AP 按配置的次数执行，默认 `n=3`。
2. 记录执行时间等 query processing metrics。
3. 多次执行的最大、平均、最小值可以聚合，避免单次缓存、系统负载或 I/O 波动导致误判。[p-0090][p-0092][p-0093]
4. 训练次数未达到 `n` 时，计划继续处于 candidate 状态。

### 4. 正常完成时的状态转移

1. 如果候选计划完成且聚合性能优于当前 best AP，candidate AP 变为 best AP。
2. 当前 best AP 转入 bad AP 列表。
3. 如果候选计划完成但性能劣于当前 best AP，candidate AP 转为 bad AP。
4. 后续优化时避免匹配 bad AP；后续执行使用 best AP。[p-0104]-[p-0112]

### 5. 查询中止时的流程

说明书 `[0194]` 和 `[0130]` 给出了中止场景：

1. candidate AP 开始执行。
2. 执行可能被 DBA 因运行过久而 abort，也可能因其它原因中断。
3. 执行引擎在中止时记录部分 `plancost`，而该功能主要需要部分 elapsed time。
4. 将已耗时间与当前 best plan 的时间比较。
5. 如果部分执行时间已经超过当前 best plan，则即使执行不完整，也足以知道该候选更差：保存其指标并将其标为 bad plan。
6. 如果部分执行时间尚未超过当前 best plan，则不能据此证明候选更差；该中断被视为 invalid execution，不更新训练对象。
7. bad plan 在以后重新出现时被跳过，使用 best plan。

该流程只证明计划级“已经慢到不可能胜出”，没有读取或判断计划树中每个节点的 A-rows。

### 6. 与本案的关系

Sybase 明确告诉我们：中断执行可以产生有用事实，而且事实可以经过“足以证明/不足以证明”的筛选。这与本案保留下界或拒绝反馈的思想相似。

但 Sybase 的事实是部分耗时，消费对象是 best/bad 计划状态；本案的事实是逐节点输出和执行状态，消费对象是下一轮独立候选的基数输入。Sybase 不能覆盖本案的节点目标绑定、未来重入判断和 `EXACT/LOWER_BOUND/NONE` 分类。

## 七、对本案核心的准确定位

五件专利分别公开了以下单独构件：

- IBM 公开了运行中检查、`EOF`、阈值和当前查询重优化；
- Oracle 公开了部分执行统计、操作级统计和未来查询重优化；
- Microsoft `US11334538B2` 公开了每节点 estimated/actual cardinality 到后续 CE feedback 的链条；
- Microsoft `US7493337B2` 公开了算子下界、上下界传播和用户 abort 入口；
- Sybase 公开了中断候选的部分性能事实和证据筛选。

本案应明确写成以下组合：

1. 先因外部单轮期限取消真实候选；
2. 在执行器清理前保存原候选计划和节点运行事实；
3. 对每个节点建立到基数目标的语义对应；
4. 结合局部 `EOF`、父链未来重入、已关闭执行时期和累计/单次调用范围，判断观测是否覆盖目标的全部相关输出；
5. 将观测分为完整值、仅能抬高估算的下界或无反馈；
6. 只将合格证据送入下一轮独立候选，并将取消候选的部分耗时与完整候选时间分开管理。

其中，最有区别性的步骤是第 4、5 步。已有专利分别讨论了检查点阈值、部分统计、上下界或中断耗时，但本文核对的五件文本没有明确给出“取消现场对全计划节点按目标级完成性和调用口径进行证据分级”的完整流程。

这也解释了为什么本案不能把 `A-rows` 直接称为“实际基数”：`A-rows` 首先只是执行器截至取消时的事实；只有在目标语义、调用范围和未来输出可能性都得到证明后，才可以把它解释为 `EXACT` 或 `LOWER_BOUND`。

## 八、一页 PPT 版：Microsoft `US7493337B2`

Microsoft / `US7493337B2` / *Query Progress Estimation*

**核心思想：** 将查询执行建模为多个 pipeline 的工作量，持续统计算子已经完成的工作量 `K`，并根据算子语义为预计总工作量 `N` 维护上下界；用修正后的总工作量估计当前查询进度。用户可以根据进度选择继续或中止查询，但中止不是该进度估计方法的必要触发条件。

**核心流程：**

- **建立工作量模型：** 将执行计划划分为多个 pipeline，选择 Scan 或 Index Scan 等 driver node；以 driver node 的预计工作量或加权工作量估计查询总工作量。
- **在线采集工作量：** 执行期间持续记录每个算子当前已经输出的 tuple 数量 `K_i`，作为已完成工作量的事实。
- **通用上界计算：** 对某个算子，先取当前已经输出的 `K_i`，再估计尚未消费的输入最多还能产生多少输出；上界通常表示为“已输出量 + 剩余输入上界 × 算子最大输出倍数”。Filter、Nested Loop、Hash Join 等算子根据各自的输入关系和物理性质使用不同规则。
- **维护下界和上界：** 已输出数量通常形成下界；Group By 可用已观察到的不同值数量收紧下界；Hash Join 可用最大 build partition 大小收紧上界；叶节点 Scan 的上下界通常直接来自表或索引大小。
- **传播并修正总工作量：** 某个节点的边界变紧后，向执行计划上方传播；如果原估算 `N_i` 小于 `LB_i` 或大于 `UB_i`，则将用于进度模型的估算约束到边界范围内。这里修正的是当前进度估计使用的工作量，不代表重新生成物理执行计划。
- **计算查询进度：** 简单 pipeline 可用 `PROG=K_1/N_1`；多个 pipeline 可用 `Σ(C_i×K_i)/Σ(C_i×N_i)`。上下界主要通过修正分母中的总工作量估计，或使用总工作量上界生成不倒退的单调进度。

**与本案的重合点：** 执行期间读取节点输出；已输出数量作为下界；按算子性质计算上下界；上下界沿计划树传播；用运行反馈修正原估算。

**与本案的区别：** 该专利的输出是当前查询的整体进度和进度显示；没有规定外部单轮期限取消后的清理前取证、目标级 `EXACT/LOWER_BOUND/NONE` 分类、父链未来重入判断，也没有把取消后的节点行数写入下一轮独立候选的 Rows 输入。

## 九、一页 PPT 版：Oracle `US11321317B2`

Oracle / `US11321317B2` / *Leveraging Query-Specific Statistics in Non-Equivalent Queries*

**核心思想：** 查询开始执行后，统计收集器可以根据已经读取的真实数据选择更合适的后续子计划；如果运行统计证明当前计划的估算严重错误，可以在计划完成前终止并换计划；如果统计具有长期价值，还可以保存给后续相关查询使用。

**核心流程：**

- **编译阶段：** 准备多个候选子计划；准备 statistic collector 和可能的 buffer。
- **执行阶段：** 先执行多个子计划共用的前置部分；统计收集器边执行边统计行数；达到决策阈值后选择后续子计划。例如，`T1` 输出少于 10 行时选择 `Index Range Scan + Nested Loop`，达到或超过 10 行时选择 `Table Scan + Hash Join`；公共前缀已经产生的结果交给被选中的子计划，未选中的子计划不再执行。[0033]-[0055]
- **运行中换计划：** 如果实际行数与估算严重偏离，例如估算 100 行而实际已产生 10,000 行，则结合剩余操作和剩余成本重新比较当前计划与替代计划；替代计划明显更优时，终止当前未完成计划并启动新计划。[0105]-[0107]
- **保存给后续查询：** 第一条查询可以完整执行，也可以只执行计划的一部分；如果某个表、连接、分组或索引操作的实际统计与估算差异足够大，就保存统计或建立 `plan directive`。后续查询匹配相关对象和操作后，使用这些统计生成新计划。[0083][0084][0087][0114]-[0117]
- **编译期采样的区别：** `dynamic sampling` 是优化器在编译期间额外执行的统计采样；上述 statistic collector 则是在原始查询已经开始执行后随计划运行的收集器，两者不是同一条流程。

**与本案的重合点：** Oracle 已公开运行中读取真实行数、部分执行、用户或系统终止长计划、误估触发的提前换计划，以及将操作级统计保存给后续查询。

**与本案的区别及保护边界：**

- **触发时机：** Oracle 的 adaptive plan 由预设决策阈值触发，in-flight reoptimization 由运行时误估和剩余成本触发，用户终止只出现在 catastrophic plan 背景中；本案由调优器为每轮独立候选设置外部执行期限，期限到达本身就是捕获部分行数证据的触发点。
- **执行边界：** Oracle 的 adaptive plan 和 in-flight reoptimization 都是在**当前查询仍在执行时**从当前计划切换到其它计划；本案不在候选内部动态换计划，而是结束第 `i` 轮候选，再为同一 SQL 生成第 `i+1` 轮候选。
- **取证时点：** 本案在取消异常展开、执行器对象清理之前保存原计划和逐节点运行状态；Oracle 所核文本没有明确要求在这一取消清理窗口内保存全树快照。
- **统计用途：** Oracle 的统计主要用于选择当前子计划、证明当前计划值得提前终止，或帮助后续查询编译；本案将候选快照中的节点行数转化为下一轮独立候选的基数输入。
- **证据判定：** 本案核对目标语义、父链未来重入、调用次数和累计/单次计数范围，将节点观测分为 `EXACT`、`LOWER_BOUND` 或 `NONE`；Oracle 主要判断统计是否足以支持当前决策或后续查询匹配，没有明确规定这套目标级证据分类。
- **时间评价：** 本案把取消候选的部分耗时与正常完成候选的完整运行时间分开；通过超时取得的节点证据可以推进下一轮规划，但不能把超时阈值当作候选完整执行时间。

*原文依据：说明书 `[0009]`、`[0033]`–`[0055]`、`[0083]`–`[0098]`、`[0105]`–`[0107]`，以及权利要求 1。*
